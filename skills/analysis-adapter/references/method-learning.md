# Learning and assessing methods

Follow design and retained data; assess methods from comparable studies for transfer and explanatory gain. Novelty, complexity or significance alone do not justify changing the analysis.

Use inspected primary method passages and relevant applications/versions to support applicability and implementation claims. Distinguish findings from inference and check "exact" assumptions. Explain data needs, cost and gain; recommend keeping, investigating or changing. The author decides; consultation needs no data or formal source.

Distinguish runner methods from reviewed external syntax. Within authorization, run useful candidates and assess added information with the author. Keep candidate artifacts separate; computing, adopting specifications/results and manuscript edits are separate decisions.

## Shared computation interface

Resolve `scripts/analysis_runner.py` from the same plugin root as the loader. `methods` lists implementations; `methods --method <name>` returns the compact field contract without reading implementation files. `run --spec <absolute-json>` checks inputs/runtime and saves a separate candidate; use `preflight --spec <absolute-json>` separately when diagnosis is needed, not as a duplicate step before every run. Read the JSON business status: exit 0 alone is not success. No installation is automatic. Host permissions remain in force.

Reuse runner provenance, sample audits and artifact references. External implementations retain actual code, inputs, settings and output in a compact reproducible record, not a parallel ledger.

## Method contracts and search coverage

Keep the six Python methods unchanged. Conditional `method_*` resources describe approved R scope, not validated backend/options. Query the selected method contract before constructing a request; unsupported combinations stay explicit. Capability queries do not start R. R and method-specific packages are optional runtime dependencies; never install automatically or silently change a formal engine. Use actual runtime/version evidence as provenance.

AnalysisSpec v3 / AnalysisRun v2 introduce `analysis_context`: `inferential_status`, `analysis_role`, `basis_ref`, `search_set_id`, `parent_analysis_id`; consult the current small method contract for the developing exact API rather than inventing commands. Statistical settings belong to scientific_spec. Preserve proposal timing and basis through outputs and adoption: new opportunities found after seeing results default EXPLORATORY; documented prior plans, replication and correction retain their actual basis; unknown timing is UNDETERMINED. Role and intent are orthogonal.

Record considered method families and distinct specifications in the current project record or method assessment. Record attempted, completed, failed, interrupted and adopted counts using existing candidate outputs, including rejected results. Numerical retries count runs, not new scientific specifications. Changes to outcome, covariates, sample/scoring, model/estimator or contrasts that can change inference need a new specification/version; routine diagnostics do not count as new methods. State the observable coverage; unknown earlier/external searches remain unknown. No parallel ledger or mandatory project setup. Counts do not mechanically define a multiplicity correction or license unlimited searching; define the question and comparison family.

Mappings cover all model/design variables; preserve original data, declared missingness and authorized aggregation. `methods --method <name>` is the source for current required fields and accepted options. Adopt specifications, results and manuscript edits separately.

Formal/verification requests additionally bind `authorization.formal_spec_hash` to `analysis_contracts.spec_hash(spec)` and retain one AUTHORITATIVE source. A declared approval hash is not evidence of user consent: reuse the actual decision. The Python runner cannot impersonate a different formal engine. A supplied execution host label is metadata, not proof of a real host trial.
