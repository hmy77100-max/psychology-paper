# Analysis registry schema

An adopted analysis entry records a stable analysis ID, research question, design tags, observation unit, variable-field map, scoring, sample, exclusions, model, covariates, estimator, software and version, Bootstrap settings, random seed, authoritative output, optional verification output, discrepancy status, user-adoption status, and manuscript synchronization locations.

Candidate methods and rejected specifications stay in existing project/candidate records, outside the formal registry. Retain considered method/specification counts and attempted/completed/failed/interrupted/adopted counts, with observable coverage and unknown earlier searches explicit. An adopted result may have one authoritative source and at most one verification source.


## Registered evidence contracts

All new entries require explicit host `--confirm-adopt`, exactly one AUTHORITATIVE source, at most one VERIFICATION source, a real formal output, content hashes and immutable references. Existing legacy records remain historical unverified records; reading them does not upgrade their evidence. Registration and computation do not authorize manuscript edits.

The default `controlled_run` evidence contract reads a completed candidate `analysis-run.json`, verifies its scientific specification/input identities and result contract, and compares registration metadata to the actual scientific snapshot. Software must match execution provenance. The six Python methods require `bootstrap` and `random_seed` to be null or `NOT_APPLICABLE`. Extended R contracts require method-specific runtime, diagnostics and resampling evidence; declared support is not numeric validation. Descriptive/scale-score estimation is `NOT_APPLICABLE` or `descriptive`; inferential alternatives match the executed specification (`two-sided`/`two-tailed`, `less`, `greater`). The original candidate file is never rewritten to mark adoption.

For author-approved results produced outside the controlled runner, use `evidence_kind: "external_analysis"`. This restores registration of SPSS/R and other external methods without claiming execution support for those methods. Keep the normal entry fields; model names are not limited to the six runner methods. Record actual external estimation, bootstrap and seed settings. `software` requires nonempty `name` and `version`; the AUTHORITATIVE source and its artifacts must identify that same software/version. Optional verification artifacts match their own source software/version, which may differ.

`external_artifacts` is a list of distinct files with `role` (`output` or `syntax`), `path`, `sha256`, `software`, and `version`. At least one output and one original syntax/code file are required. `formal_output` must identify a listed output. There is no software, method or filename-extension whitelist: external Python permutation results in JSON and R outputs in TXT/CSV/HTML can be registered. File extensions do not prove execution origin or authenticity. Explicit author adoption attests the described origin, recorded as `origin_status: "AUTHOR_ATTESTED"` in the saved reference. These checks establish file existence and byte integrity only; they do not establish that the code is valid, that it was executed, or that it generated the supplied output. An unsupported origin-status claim cannot upgrade the saved evidence level.

A manually transcribed p-value table alone is insufficient: the distinct original code/syntax artifact and explicit author adoption are still required. Even when both are supplied, registration does not automatically claim computational validation or independent numeric verification.

The external `spec_hash` is SHA256 of UTF-8 JSON with sorted keys, compact separators, Unicode preserved and nonfinite numbers forbidden, over exactly these entry keys: `research_question`, `design_tags`, `observation_unit`, `field_map`, `scoring`, `sample`, `model`, `software`, `estimation`, `bootstrap`, `random_seed`, `input_hash`. `input_hash` records the author's input-content SHA256 claim; this registration does not rerun the input or verify its numeric relationship to the output. Each actual artifact must match its declared SHA256; all artifact hashes are checked again immediately before registration and by project validation afterwards. Saved `formal_output_ref` binds analysis identity, scientific specification/input hashes and the complete artifact-reference list.

The resulting evidence level is always `EXTERNAL_ARTIFACTS_REGISTERED_NUMERICS_UNVERIFIED`. Numeric/backend validation and independent verification are not claimed. A source role `VERIFICATION` records its intended use, not successful verification. The author may select the external result as formal without changing its origin or upgrading its evidence. Existing lock/conflict/atomic-write protections apply to both contracts.


An external entry may retain at most one `VERIFICATION` source alongside its AUTHORITATIVE source. When a verification source is present, all sources need distinct nonempty `source_id`, software and version; every artifact needs an explicit `source_id` and must match that source's software/version. Without a verifier, artifact source IDs remain optional for compatibility. Formal output and original formal code must belong to the AUTHORITATIVE source. `verification_output` must resolve to an existing, hash-matching output artifact belonging to the VERIFICATION source. Source identities, roles and all file references are preserved in `formal_output_ref` and rechecked by project validation.

External `discrepancy_status` is always `NOT_ASSESSED`; a caller-supplied `ALIGNED` or other upgraded claim is rejected. Registration does not compare numeric results. Verification code is optional: the saved reference explicitly reports `UNVERIFIED_CODE_NOT_PROVIDED` when absent, or `UNVERIFIED_CODE_REGISTERED` when supplied. Both describe an unverified process. Neither source purpose nor code/output existence establishes equal scientific specifications, actual execution, numeric agreement, or independent verification. No new execution/comparison engine is involved.

AnalysisSpec v3 / AnalysisRun v2 carry `analysis_context`: `inferential_status`, `analysis_role`, `basis_ref`, `search_set_id`, `parent_analysis_id`, and boolean `discovered_after_results`. Preserve this proposal-time basis through adoption and source references; do not rewrite a candidate file. New opportunities after viewing results default EXPLORATORY, documented prior-plan replication/correction keeps its basis, and unknown timing is UNDETERMINED. Roles remain orthogonal to the four intents. Historical absent context stays unknown; do not backfill a single attempted analysis. Use the current contract for exact field values. For direct models, optional `sample.n` and result `n` count analyzed rows; repeated-design `n_subjects`, grouping counts and post-aggregation `model_rows` are reported separately and must not be described as interchangeable sample sizes.
